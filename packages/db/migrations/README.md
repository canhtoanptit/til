# Migrations policy

Read this before adding a migration. It exists because the "hand-written precedent" here is
non-obvious and has been rediscovered from scratch several times.

## How migrations are written

**Hand-number a new `.sql` file and write the SQL yourself.** That is the normal path, not the
exception. Only `0000_init`, `0002_digests` and `0003_vectors` were ever generated by drizzle-kit;
`0001_fts` and `0004`–`0011` are hand-written, because most of what this schema needs — FTS5
virtual tables and their sync triggers, backfills, column adds with data migration — is
something drizzle-kit cannot generate ([ADR-0009](../../../docs/adr/0009-retrieval-insight-layer.md)).

Naming: `NNNN_short_name.sql`, four digits, zero-padded, no gaps.

- **Next free number: `0012`** — but see the reservation below.
- **Reserved: `0012_email`** for P27 (email delivery + email-in capture), deferred by the owner
  pending a custom domain for Cloudflare Email Routing. If you ship an unrelated migration before
  P27 ever lands, take `0012` and let P27 take the next number — the reservation is a courtesy, not
  a constraint.

## How migrations are applied

**By filename sort, all `.sql` files, every time.** Both consumers agree on this and neither reads
any metadata:

- Production/local D1: `wrangler d1 migrations apply til` via `migrations_dir` in
  `apps/web/wrangler.jsonc`.
- Tests: `applyMigrations()` in `../test/migrations.test.ts` does
  `readdirSync(...).filter(f => f.endsWith(".sql")).sort()` against a `better-sqlite3` in-memory DB.

Consequences worth knowing:

- Non-`.sql` files in this directory (this README, `meta/`) are ignored by both. Safe to keep here.
- **Never split migration SQL on `;`** — trigger bodies contain semicolons. Execute whole files, or
  use drizzle's `--> statement-breakpoint` markers.
- Migrations must be append-only. An already-applied file is frozen; fix it with a new migration.

## `meta/` is frozen — do not trust it, do not run `db:generate` casually

`meta/` holds drizzle-kit's snapshot state (`_journal.json` + `NNNN_snapshot.json`). It is **kept,
not maintained**:

- drizzle-kit **is** still installed and configured (devDependency `drizzle-kit@0.31.10`,
  `./drizzle.config.ts`, `pnpm db:generate`), which is why these files are kept rather than deleted
  — deleting them would silently change what `db:generate` produces.
- The journal is **stale on purpose**. It records only `0000`, `0002`, `0003`. Every hand-written
  migration since is invisible to it, and nothing backfills it.

**The footgun:** running `pnpm db:generate` today diffs `src/schema.ts` against the `0003` snapshot,
so it emits one enormous migration that tries to re-create everything added in `0004`–`0011`.
That output is wrong and must not be committed. If you genuinely want drizzle-kit to generate a
diff again, you would first have to bring `meta/` back in sync with the real schema — treat that as
its own deliberate task, not a side effect of adding a table.

In practice: **hand-write the SQL.** `db:generate` is kept for reference and for the day someone
re-syncs the snapshots.
